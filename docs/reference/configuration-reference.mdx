# Configuration Reference

TokenStream configuration is split by runtime boundary. Provider and policy records govern model access, corpus and source records govern retrieval scope, processor records govern ingestion adaptation, and environment variables wire services together.

<Note>
For exact schemas, use the checked-in OpenAPI contracts under `docs/`. This page explains the ownership model and defaults operators usually need while configuring ingestion, chunking, and embedding.
</Note>

## Runtime configuration sources

| Source | Owns | Examples |
| --- | --- | --- |
| Provider records | Available LLM providers and capabilities | `name`, `base_url`, `models`, `default_model`, `capabilities.chunking` |
| Pipeline policies | Request routing and allowlists | `pipeline_id`, `allowed_providers`, `allowed_models`, `default_provider`, `default_model`, `chunking` |
| Corpus records | Retrieval boundary and generic chunk shape | `corpus_id`, `chunking`, `processor_id`, `processor_config`, `retrieval_config` |
| Source records | Source location and source-level overrides | `source_id`, `type`, `format`, `url`, `object_uri`, `processor_id`, `processor_config`, `metadata` |
| Processor records | Ingestion adapter and reusable adapter config | `processor_id`, `type`, `config`, `enabled` |
| Ingestion jobs | One ingestion run and run-level overrides | `pipeline_id`, `source_ids`, `force_reembed`, `processor_id`, `processor_config`, `configuration.chunking_model` |
| Environment variables | Service wiring and operational limits | `EMBEDDER_URL`, `INGESTION_PIPELINE_ID`, `PROCESSOR_REGISTRY_PATH`, `ORCHESTRATOR_API_URL` |

## Ingestion configuration

An ingestion job controls the current run. It is created through the management API and then claimed by `ingestion-worker`.

| Field | Effect |
| --- | --- |
| `pipeline_id` | Selects the policy used when the worker calls `orchestrator-api` for LLM chunking. If omitted, the worker uses `INGESTION_PIPELINE_ID`, defaulting to `default`. |
| `source_ids` | Restricts ingestion to selected sources. Omit or use `null` to process the whole corpus. |
| `force_reembed` | Forces chunk and embedding regeneration instead of skipping unchanged sources. |
| `processor_id` | Overrides the source or corpus processor for this run. |
| `processor_config` | Adds run-level processor config and is merged last. |
| `configuration.chunking_model` | Selects the LLM model used for chunking for this run. The browser UI stores the selected chunking model here. |

<Warning>
Registering or uploading a source does not make it searchable by itself. Searchable retrieval artifacts appear only after an ingestion job fetches, parses, chunks, embeds, and indexes that source.
</Warning>

## Processor configuration

Processor configuration defines how source material is parsed or converted before embeddings are generated. Processor records are top-level registry objects with a stable `processor_id`, an adapter `type`, and reusable `config`.

Processor selection is resolved in this order:

1. Ingestion job `processor_id`
2. Source `processor_id`
3. Corpus `processor_id`
4. `default`

Processor configuration is merged in this order, with later layers overriding earlier layers:

1. Top-level processor record `config`
2. Corpus `processor_config`
3. Source `processor_config`
4. Ingestion job `processor_config`

| Processor type | Behavior | Important config |
| --- | --- | --- |
| `default` or `generic` | Uses the generic parser and LLM chunking path. | Corpus `chunking`; optional job `configuration.chunking_model` |
| `structured_archive` | Reads zip or tar snapshots, applies include/exclude rules, decodes text-like files, and emits citation-ready metadata. | `include`, `exclude`, `max_file_bytes`, `max_files`, `max_chunk_chars`, `metadata_defaults` |

## Chunking configuration

There are two different `chunking` concepts.

### Corpus `chunking`

Corpus `chunking` controls chunk shape for the generic processor.

| Field | Effect | Default |
| --- | --- | --- |
| `strategy` | Chunking strategy. The supported production path is `llm`. | `llm` |
| `target_chars` | Target size for chunks generated from parsed blocks. | `2200` |
| `overlap_chars` | Overlap guidance passed to the chunking helper. | `250` |
| `model` | Optional fallback model when no job `configuration.chunking_model` and no `pipeline_id` are supplied. | unset |

### Pipeline `chunking`

Pipeline policy `chunking` controls whether `orchestrator-api` may serve internal `task=chunking` requests and which providers/models are allowed or default for those requests. It does not define source parsing rules, file include/exclude behavior, or embeddings.

| Field | Effect |
| --- | --- |
| `enabled` | Allows or blocks chunking requests for the selected policy. |
| `default_provider` | Provider used when the chunking request does not specify one. |
| `default_model` | Model used with the default chunking provider. |
| `allowed_providers` | Provider allowlist for chunking requests. |
| `allowed_models` | Model allowlist for chunking requests. |

When `ingestion-worker` calls `orchestrator-api` for LLM chunking, the request includes `task=chunking` and the selected `pipeline_id`. The orchestrator enforces the matching pipeline chunking policy and the provider's `capabilities.chunking` flag.

## Embedding configuration

Embedding is controlled by the embedding service and worker environment, not by corpus `chunking` or `processor_config`.

| Setting | Owner | Effect | Default |
| --- | --- | --- | --- |
| `EMBEDDER_URL` | `ingestion-worker` and `retrieval-api` | Endpoint used for embedding requests. | Required in the worker |
| `EMBED_BATCH_SIZE` | `ingestion-worker` | Number of chunk texts sent per embedding batch. | `6` |
| `EMBED_TIMEOUT_SECONDS` | `ingestion-worker` | HTTP timeout for embedding calls. | `600` |
| `EMBED_MAX_CHARS` | `ingestion-worker` | Maximum characters per text sent to the embedder. | `8000` |
| `MODEL_ID` | `tei-embedder` | Embedding model loaded by Text Embeddings Inference in the compose stack. | Compose example uses `intfloat/multilingual-e5-small` |

## Quick mental model

- Job request fields decide what to ingest now and which run-level overrides apply.
- Processor config decides how source material is parsed or adapted.
- Corpus `chunking` decides chunk shape for the generic processor.
- Pipeline `chunking` decides which LLM route may be used for chunking.
- Embedder environment decides how chunk text becomes vectors.
