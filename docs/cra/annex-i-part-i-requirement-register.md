# TokenStream CRA Requirement Register: Annex I Part I

Status: Draft
Date: 2026-08-26
Scope: TokenStream open-source, non-commercial software distribution; voluntary CRA readiness/certification evidence only. This register does not assert formal CRA conformity, EU Declaration of Conformity, or CE marking.

## Method

This register starts from the Cyber Resilience Act (Regulation (EU) 2024/2847) Annex I Part I requirements and interprets them for TokenStream before defining controls. OpenChain is used only as an implementation and evidence cross-check, not as the normative source of requirements.

Applicability in this document means applicability inside the voluntary TokenStream CRA readiness scope, not a legal conclusion that the current open-source, non-commercial distribution is placed on the EU market.

## Product Context

TokenStream is a software-only AI orchestration and retrieval runtime. It sits behind client applications and provides OpenAI-compatible API endpoints, provider/model routing, policy enforcement, MCP tool orchestration, corpus/source management, ingestion jobs, hybrid lexical/vector/graph retrieval, machine API keys, human admin authentication, and a browser admin UI.

The assessed deployment model is a self-hosted Docker Compose stack with `dev-ui`, `orchestrator-api`, `retrieval-api`, `ingestion-worker`, Qdrant, MinIO-compatible object storage, SQLite-backed registry/index data, optional Open WebUI, external LLM providers, and optional MCP servers.

Relevant protected assets include provider credentials, machine API keys, session tokens, admin user records, policy/provider/corpus configuration, uploaded source documents, raw fetched source material, generated chunks, embeddings, retrieval indexes, logs, and model/tool request metadata.

## Applicability Register

| Requirement ID | CRA source | Requirement statement | TokenStream interpretation | Applicability | Applicability rationale | Required security capability |
| --- | --- | --- | --- | --- | --- | --- |
| REQ-CRA-AI-1 | Annex I Part I (1) | The product must provide an appropriate level of cybersecurity based on the risks. | TokenStream's design, default deployment topology, API boundaries, dependency choices, release process, and runtime configuration must be justified by a product cybersecurity risk assessment. | Applicable | TokenStream exposes administrative and machine APIs, stores security-relevant configuration and corpus data, connects to external providers/tools, and creates retrieval indexes. Even in a non-commercial OSS scope, a risk-based baseline is needed before interpreting the detailed Annex I Part I requirements. | Product cybersecurity risk assessment; threat model; asset and data-flow inventory; security requirements traceability. |
| REQ-CRA-AI-2A | Annex I Part I 2(a) | The product must not be released with known exploitable vulnerabilities. | A TokenStream release should not ship with an unresolved vulnerability that is known and exploitable in the TokenStream product context, including application code, containers, Python/npm dependencies, base images, and bundled configuration. | Applicable | TokenStream is dependency-heavy and containerized. Known vulnerabilities may arise from FastAPI/Starlette/httpx, React/Vite/npm packages, LLM client libraries, Qdrant/MinIO/Open WebUI images, TEI images, and Docker base images. Exploitability must be assessed in context rather than inferred from CVE presence alone. | Vulnerability identification; dependency and container scanning; exploitability assessment; remediation or documented risk acceptance; release decision gate. |
| REQ-CRA-AI-2B | Annex I Part I 2(b) | The product must be secure by default and resettable to its original state. | Default configuration should avoid default credentials, unnecessary public exposure, unsafe provider/tool access, permissive corpus access, or insecure cookies/secrets; operators should be able to restore a known-good baseline configuration. | Applicable | The local stack currently includes environment-driven secrets, admin bootstrap behavior, exposed ports, MCP/tool allowlists, provider registries, policy files, object storage, and runtime snapshots. Secure defaults and reset/restore matter because misconfiguration can expose data, tools, credentials, or management functions. | Secure default configuration; bootstrap credential handling; configuration baseline and restore; hardening guidance; reset/recovery procedure for registry/runtime state. |
| REQ-CRA-AI-2C | Annex I Part I 2(c) | Vulnerabilities must be addressable through security updates, including automatic updates where applicable. | TokenStream must have a way to deliver and document security updates for source releases and container images. Automatic update is deployment-model dependent and should not be assumed for self-hosted OSS installs unless an updater is provided. | Applicable with deployment-model qualification | Users deploy TokenStream from source and/or container images. Security fixes can be delivered by GitHub releases, container tags, changelog/advisories, and upgrade instructions. The current project should document whether automatic updates are out of scope for self-hosted deployments and how users are notified. | Security release process; versioning and advisory process; update integrity; upgrade documentation; user notification; automatic-update applicability decision. |
| REQ-CRA-AI-2D | Annex I Part I 2(d) | The product must protect against unauthorised access and report possible unauthorised access. | TokenStream must enforce authentication, authorization, scopes, RBAC, corpus boundaries, policy restrictions, and internal service authentication; it must also produce security-relevant events for suspected unauthorised access. | Applicable | TokenStream has human admin sessions, machine API keys, scoped management permissions, runtime API key checks, pipeline policy allowlists, internal reload/registry tokens, and corpus-scoped retrieval. Unauthorized access could expose provider credentials, corpora, source documents, tools, or LLM routes. | Authentication; authorization; RBAC/scope enforcement; internal service authentication; tenant/corpus isolation; unauthorised-access logging and alerting. |
| REQ-CRA-AI-2E | Annex I Part I 2(e) | The product must protect confidentiality of stored, transmitted, or otherwise processed data. | TokenStream must protect secrets, admin data, corpus sources, generated chunks, embeddings, retrieval results, provider/tool payloads, and runtime snapshots in transit and, where risk requires, at rest. | Applicable | The stack handles sensitive credentials and potentially private documents. It also transmits prompts, retrieval chunks, MCP tool payloads, and model-provider requests across service and external network boundaries. Local Docker examples may rely on operator-controlled networks, so production confidentiality requirements must be explicit. | Data classification; TLS/reverse-proxy requirements; secret storage/reference model; at-rest protection decision; log redaction; provider/tool data-flow controls. |
| REQ-CRA-AI-2F | Annex I Part I 2(f) | The product must protect integrity of data, commands, programs, and configuration and report corruptions. | TokenStream must protect registry records, policies, provider definitions, processors, retrieval profiles, uploaded source hashes, generated indexes, runtime snapshots, release artifacts, and administrative commands against unauthorised or corrupted modification. | Applicable | Product behavior is strongly configuration-driven. Manipulated policy/provider/corpus records or poisoned retrieval indexes could redirect model calls, expose tools, alter source-backed context, or corrupt outputs. The management API also includes source deletion/purge and job cancellation flows. | Configuration integrity; release artifact integrity; source/content hashing; index consistency checks; change audit trail; corruption/error reporting. |
| REQ-CRA-AI-2G | Annex I Part I 2(g) | The product must process only data necessary for its intended purpose. | TokenStream should limit collection, retention, transmission, indexing, logging, and provider/tool forwarding to data needed for orchestration, retrieval, administration, and diagnostics. | Applicable | TokenStream ingests source documents, stores raw files, creates chunks/embeddings, forwards prompts/context to LLM providers, and may invoke external MCP tools. Without minimisation, deployments can over-index, over-log, or send unnecessary context to external services. | Data inventory; purpose mapping; corpus/source scoping; retrieval limit enforcement; prompt/context minimisation; retention and logging limits. |
| REQ-CRA-AI-2H | Annex I Part I 2(h) | The product must protect availability of essential and basic functions, including after incidents and against denial-of-service. | TokenStream should maintain availability of essential functions such as admin access, API request handling, corpus readiness, ingestion recovery, retrieval queries, and configuration restore within the expected self-hosted deployment model. | Applicable | The architecture contains multiple dependent services. Availability can be affected by provider failure, embedding service failure, Qdrant/SQLite/MinIO issues, ingestion job failures, malformed input, heavy uploads, tool loops, or denial-of-service against public ports. | Resilience architecture; timeouts and bounded retries; rate/size limits; health checks; job recovery; backup/restore; incident recovery procedure. |
| REQ-CRA-AI-2I | Annex I Part I 2(i) | The product must minimise negative impact on availability of other devices or networks. | TokenStream should avoid becoming a source of excessive traffic or cascading failures against model providers, MCP servers, object storage, embedding services, vector databases, client networks, or connected internal tools. | Applicable | TokenStream can fan out to LLM providers, MCP tools, retrieval services, embedding services, and storage. Misconfigured ingestion, unbounded tool rounds, retries, large uploads, or repeated queries could overload connected services. | Outbound rate limiting; bounded concurrency; retry/backoff discipline; tool-loop limits; ingestion limits; circuit breaking or fail-fast behavior; operator guidance. |
| REQ-CRA-AI-2J | Annex I Part I 2(j) | The product must limit attack surfaces, including external interfaces. | TokenStream should expose only necessary endpoints and ports by default, clearly distinguish public, admin, and internal APIs, and disable or restrict optional surfaces such as MCP, direct retrieval, Open WebUI, bootstrap admin, and object storage consoles. | Applicable | The Compose stack exposes several ports and services. Documentation already distinguishes normal facade access from trusted/internal service access, and notes gaps around corpus upload hardening. Attack-surface management is central to safe deployment. | External interface inventory; default-deny exposure; network segmentation; optional feature gating; upload/source validation; hardening guide. |
| REQ-CRA-AI-2K | Annex I Part I 2(k) | The product must reduce the impact of incidents through appropriate mitigation mechanisms and techniques. | TokenStream should be designed so compromise or malfunction of one runtime boundary does not unnecessarily compromise all corpora, providers, tools, or administrative functions. | Applicable | TokenStream aggregates sensitive assets behind one runtime. A vulnerability in dev-ui, orchestrator-api, retrieval-api, ingestion-worker, a parser, an MCP server, or a provider integration could otherwise propagate across the stack. | Least privilege; service isolation; scoped keys; corpus/policy boundaries; secret separation; safe parser execution; blast-radius reduction; incident containment. |
| REQ-CRA-AI-2L | Annex I Part I 2(l) | The product must provide security-related information by recording and monitoring relevant internal activity, with a user opt-out mechanism. | TokenStream should record security-relevant activity such as auth events, admin changes, API-key use, policy/provider changes, source upload/delete, ingestion status, runtime reloads, retrieval failures, and tool/provider errors; opt-out must be assessed for self-hosted logging/telemetry. | Applicable with telemetry qualification | Existing docs mention logs and operational status, but not a complete security audit log or opt-out model. Because TokenStream is self-hosted, local operational logging may be required for security, while any optional outbound telemetry should be explicit and opt-out capable. | Audit logging; security event taxonomy; monitoring hooks; log retention/redaction; opt-out decision for telemetry; admin-visible activity review. |
| REQ-CRA-AI-2M | Annex I Part I 2(m) | Users must be able to securely and easily remove all data and settings permanently, and securely transfer data where applicable. | TokenStream should let operators remove or export corpus metadata, source records, uploaded object bytes, generated indexes, runtime configuration, users, sessions, API keys, and local volumes in a documented and verifiable way. | Applicable | TokenStream stores data across SQLite, MinIO/object storage, Qdrant, lexical SQLite files, runtime snapshots, local volumes, and optional Open WebUI storage. The management API has some deletion/export/import behavior, but complete permanent deletion and secure transfer need explicit coverage. | Secure deletion; purge of generated artifacts; registry export/import; backup/restore and migration; decommissioning procedure; verification of data removal. |

## OpenChain Cross-Check Anchors

OpenChain should be used as a cross-check after this register, especially for:

- §3.4 Secure Development Properties & Security Testing: secure defaults, attack surface minimisation, encryption, memory-safety rationale, SAST/DAST/fuzzing, threat modelling, and release security gate.
- §4.1-§4.3 Vulnerability Handling: vulnerability monitoring, exploitability assessment, remediation criteria, escalation, and vulnerability register.
- §6.1 Support Period & Update Obligations: support period, security update availability, update delivery mechanism, and end-of-support communication.
- §7.1-§7.2 Technical File and downstream provisioning: risk assessment, technical documentation, security-test evidence, user-facing instructions, and downstream update/support information.

These references are implementation and evidence prompts only. If an OpenChain item is not traceable to a TokenStream requirement, it should be treated as a good-practice candidate or evidence idea, not as an automatically applicable CRA control.
